## Очистка денежных строк в Power Query

В Excel встречаются строки вида «2 781.82», а в копии «2 781,82». Сначала удаляются обычные, неразрывные и узкие неразрывные пробелы. Затем запятая заменяется точкой и выполняется явное преобразование с культурой en-US. Не следует полагаться на автоматическое определение типов в русской локали.

```
// Функция fxNumber в Power Query
(x as any) as nullable number =>
if x = null then null
else if Value.Is(x, type number) then x
else Number.FromText(
    Text.Replace(
        Text.Remove(Text.Trim(Text.From(x)),
            {" ", Character.FromNumber(160),
             Character.FromNumber(8239)}),
        ",", "."), "en-US")
```

Выручка уже является суммой строки. Повторное умножение на количество завысит результат. Прибыль также готова в источнике. Себестоимость не дана; нельзя заменять прибыль формулой с выдуманной себестоимостью.

Календарь непрерывен с 1 января по 31 декабря 2022 года и покрывает все продажи. Поля Год, Месяц и МесяцГод поддерживают хронологическую сортировку. В Desktop следует пометить его таблицей дат по Date. Для текущего задания не нужны даты 2010–2030: они только добавляют пустые периоды.

## Почему менеджер хранится в регионе

В исходном справочнике каждому региону назначен один менеджер. Поля Manager, Region, Страна и условные координаты объединены в d_Регионы. Покупатель или Order_ID не используются для привязки менеджера: таких назначений источник не содержит.

## Иерархия номенклатуры

В d_Продукты созданы уровни Category → Subcategory → Product. Связь с фактами проходит только по Product. Иерархия и три поля на оси диаграммы дают переход от категории к подкатегории и товару. При drill-down фильтры даты, региона и покупателя сохраняются.

## Служебные таблицы

«Меры» — отдельная таблица с одним скрытым техническим столбцом и 18 мерами, включая динамическую SVG-карту. d_ABC содержит три строки A, B, C и не имеет физических связей. Она задаёт желаемую группу для специальных мер, которые заново классифицируют товары в текущем контексте фильтров. Фиксированного столбца ABC в справочнике нет: он стал бы неверным при выборе другого периода.

Проверка модели: ключи стороны «один» уникальны, все ключи фактов имеют соответствие, число фактов после соединений остаётся 730. Использование однонаправленных связей исключает непредвиденную фильтрацию между справочниками.

## Выручка

```

```


Сумма исходной прибыли — 253 784,61. Логистика дополнительно не вычитается: состав исходной прибыли не раскрыт.

## Рентабельность

```
Рентабельность = DIVIDE([Прибыль], [Выручка])
```

Отношение суммы прибыли к сумме выручки, формат 0,00%. Итог — 23,00%. Среднее процентов строк или месяцев здесь неверно. При нулевой выручке DIVIDE возвращает BLANK.

## АКБ

```
АКБ = DISTINCTCOUNT('f_Продажи'[Buyer])
```

Число разных покупателей с продажами в выбранном контексте — 173. Один клиент может покупать в нескольких категориях, поэтому суммы АКБ по категориям не равны общему АКБ.

## Средний чек

```
Заказы = DISTINCTCOUNT('f_Продажи'[Order_ID])
Средний чек = DIVIDE([Выручка], [Заказы])
```

Выручка разделена на 571 уникальный заказ. Получаем 1 932,15. Деление на 730 строк даст среднюю выручку строки, а не чек заказа.

## Затраты на логистику

```
Затраты на логистику = SUMX('f_Продажи', RELATED('d_Доставка'[Стоимость]))
```

Тариф подтягивается через RELATED по уникальному методу доставки и начисляется на строку. 151 × 10 + 579 × 5 = 4 405. Это определение соответствует приложенному чек-листу. Тариф на заказ без дополнительных правил неоднозначен.

# 7 Логика ABC анализа

ABC строится по выручке номенклатуры в выбранном периоде. Пороги приняты 80% для A и 95% для A+B. Они не заданы в ТЗ, поэтому правило явно зафиксировано. Рассматриваются товары с положительной выручкой; в исходной базе все продажи имеют положительную выручку.

## Последовательность расчёта

1. Сгруппировать продажи по товару и просуммировать выручку. 2. Отсортировать по убыванию выручки; при равенстве использовать название товара. 3. Рассчитать долю товара в сумме выбранной номенклатуры. 4. Рассчитать накопленную долю до текущего товара. 5. Назначить A, если доля до товара меньше 80%; B, если меньше 95%; иначе C.

Выбрано правило включения товара, пересекающего порог, в предыдущую группу. Например: доля до товара 79,8%, после товара 80,2% — товар относится к A. Поэтому фактическая выручка A может немного превышать 80%. При точном значении доли до товара 80% следующий товар попадает в B, а при 95% — в C.

| Группа | Товаров | Выручка | Доля выручки | Прибыль |
|---|---|---|---|---|
| A | 114 | 883 261,44 | 80,06% | 157 930,67 |
| B | 123 | 165 427,65 | 14,99% | 9 014,16 |
| C | 208 | 54 567,22 | 4,95% | 86 839,78 |

114 товаров группы A формируют 80,06% выручки. Группа B содержит 123 товара и даёт 14,99%. Группа C содержит 208 товаров и даёт 4,95%. Группы покрывают все 445 товаров; сумма выручки равна контрольному итогу.

## Почему доля рассчитывается через ALLSELECTED

ALLSELECTED снимает контекст текущей строки номенклатуры и сохраняет выбор пользователя. Если выбрать регион, сегмент или период, база сравнения изменится. ALL по справочнику снял бы также часть выбранных ограничений и мог дать другой смысл доли. Для данного отчёта используется ABC внутри выбранной номенклатуры.

Ранг DENSE приведён как справочная мера: при одинаковой выручке товары имеют одинаковый ранг. Для накопления используется дополнительная сортировка по названию, поэтому каждая позиция получает определённое место. Нельзя строить накопление только по плотному рангу, игнорируя равенства.

# 8 Меры ABC и контекст фильтра

## Класс товара

```
ABC товара =
VAR CurrentProduct = SELECTEDVALUE('d_Продукты'[Product])
VAR CurrentRevenue = [Выручка]
VAR Universe = FILTER(ADDCOLUMNS(ALLSELECTED('d_Продукты'), "@Revenue", CALCULATE([Выручка])), [@Revenue] > 0)
VAR RevenueBefore = SUMX(FILTER(Universe, [@Revenue] > CurrentRevenue ||
    ([@Revenue] = CurrentRevenue && 'd_Продукты'[Product] < CurrentProduct)), [@Revenue])
VAR ShareBefore = DIVIDE(COALESCE(RevenueBefore, 0), SUMX(Universe, [@Revenue]))
RETURN IF(ISINSCOPE('d_Продукты'[Product]) && CurrentRevenue > 0,
    SWITCH(TRUE(), ShareBefore < 0.8, "A", ShareBefore < 0.95, "B", "C"))
```

Universe — все выбранные товары с их выручкой. RevenueBefore суммирует выручку товаров перед текущим. CALCULATE внутри ADDCOLUMNS переводит контекст строки товара в контекст фильтра. Без этого все товары могли бы получить одну и ту же общую сумму.

## Группировка по классам

Обычную текстовую меру нельзя поставить на ось категории как вычисляемый столбец. Для групповой таблицы используется несвязанная d_ABC. Меры «Выручка ABC», «Прибыль ABC», «АКБ ABC» и «Логистика ABC» строят виртуальную классификацию, выбирают товары нужного класса и применяют их через TREATAS и KEEPFILTERS.

АКБ по классу считается после отбора всех товаров класса одним DISTINCTCOUNT, а не складывается из АКБ отдельных товаров. Это предотвращает повторный счёт клиента внутри класса. Один клиент всё равно может встречаться в нескольких классах; общий итог пересчитывается отдельно.

## Поведение при фильтрации

Период или регион меняет выручку товаров и их класс. Поэтому групповые меры пересчитывают ABC, а не используют статическую классификацию. Независимый расчёт analyze.py сохраняет контрольный CSV «ABC номенклатуры.csv» для полного периода; в Power BI классы вычисляются мерами в текущем контексте фильтров.

Полный текст всех 18 мер приведён в «Меры DAX.txt» и в model.bim. Для дальнейшей эксплуатации большие объёмы потребуют проверки производительности: виртуальная классификация выполняет сравнение товаров между собой. Для 445 товаров это небольшой объём, групповые результаты проверены запросом DAX в Desktop.

# 9 Убыточные заказы и менеджеры

Сначала определяется прибыль всего заказа в текущем контексте, затем проверяется условие меньше нуля. Фильтр Profit < 0 на исходных строках даст другой показатель: заказ с отрицательной строкой может иметь положительную итоговую прибыль.

```
Убыточные заказы =
VAR T = FILTER(VALUES('f_Продажи'[Order_ID]), CALCULATE([Прибыль]) < 0)
RETURN COUNTROWS(T)
```

```
Прибыль убыточных заказов =
VAR T = FILTER(VALUES('f_Продажи'[Order_ID]), CALCULATE([Прибыль]) < 0)
RETURN SUMX(T, CALCULATE([Прибыль]))
```

## Настройка визуалов

Карточки берут значения только из мер. В динамике ось — Календарь[МесяцГод], значения — выручка и прибыль; проценты при необходимости выводятся отдельным графиком. Для сегментов используются d_Покупатели[Segment] и меры, а не неочищенный справочник.

На диаграмме номенклатуры размещены Category, Subcategory и Product в порядке детализации. Для проверки включите drill-down и последовательно раскройте категорию, подкатегорию и товар. Все уровни должны отражать одни и те же отфильтрованные факты.

Карта Канады представляет собой SVG с границами провинций, отображаемый в нативной таблице Power BI. Она пересчитывается по фильтрам и выбранному KPI. Однозначно сопоставлены Ontario, Nunavut и Northwest Territories; агрегированные West, Atlantic и Prarie не распределялись по провинциям без подтверждённого правила. Остальные территории показаны серым. Клик по SVG не выбирает регион.

Таблица менеджеров содержит имя, число убыточных заказов и прибыль этих заказов. Во всех шести менеджерах текущего полного периода есть убыточные заказы. При необходимости в Desktop задайте визуальный фильтр «Убыточные заказы > 0», чтобы при другом периоде скрывать менеджеров без убытков.

## Переключение показателей на одной странице

Нативный кнопочный срез с единственным выбором покрывает области шести карточек. Обычный клик по числу или подписи выбирает строку независимой таблицы «Показатели». Меры SELECTEDVALUE и SWITCH меняют динамику, сравнение сегментов, номенклатуру и карту. Чёрная полоса отмечает выбранный показатель; даты сохраняются. ABC и таблица убыточных заказов сохраняют своё назначение.

# 12 Краткий конспект для защиты

## Как объяснить работу за две минуты

Я проверила Excel-базу и собрала модель «звезда» с 730 строками продаж. Рассчитала выручку, прибыль, рентабельность, активных клиентов, средний чек и логистику мерами. Средний чек использует уникальные заказы, а рентабельность — отношение общих сумм. Добавила динамику, сегменты, детализацию номенклатуры, карту, ABC и убыточные заказы по менеджерам.

В источнике обнаружились противоречивые сегменты у 18 покупателей и заказы с несколькими регионами и методами доставки. Неоднозначные сегменты выделены отдельно, чтобы не удвоить продажи. Логистика начисляется на строку по определению чек-листа. Убыточность проверяется после суммирования прибыли заказа. ABC меняется вместе с фильтрами периода и региона.

## Вопросы и короткие ответы

| Вопрос | Ответ |
|---|---|
| Почему мера, а не столбец? | Мера вычисляется в контексте фильтров пользователя. |
| Почему не AVERAGE выручки? | Строка продажи и заказ имеют разную детализацию. |
| Почему не среднее рентабельностей? | Правильный итог — общая прибыль / общая выручка. |
| Зачем CALCULATE? | Меняет фильтр и переводит контекст строки в фильтр. |
| Что делает RELATED? | Берёт тариф с уникальной стороны связи. |
| Зачем ALLSELECTED в ABC? | Сохраняет выбор пользователя и снимает строку товара. |
| Почему итог АКБ не сумма строк? | Один покупатель встречается в нескольких группах. |
| Почему 277, а не 368? | 277 — убыточные заказы, 368 — отрицательные строки. |
| Почему у менеджеров сумма 279? | Часть заказов распределена по разным регионам. |
| Почему выручка не как на скрине? | Контрольный источник даёт другую сумму; разница раскрыта. |
